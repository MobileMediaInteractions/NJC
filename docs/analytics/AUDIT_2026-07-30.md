# Ground-up statistical audit — July 30, 2026

## Decision

The original Studio totals were arithmetically consistent with their database
queries but were not suitable as claims about people, devices or application
versions. They are now treated as provisional legacy evidence. Calculation
version 2 starts an event-backed, reproducible baseline rather than attempting
to manufacture precision from aggregates that cannot support it.

## Reported discrepancy

The pre-audit Studio screenshots displayed:

- 15 tracked installations;
- 13 web installations;
- two Roku installations;
- three account links;
- three installations active in 24 hours;
- 13 installations active in seven days;
- 101 site views and 31 story views.

The known early-use control was approximately two people, with one person
having used two Roku/Roku TV application versions.

## Root causes established from the repository

1. **“Installation” was visually close to “user.”** The web client created a
   random ID per consenting browser storage profile. Clean browser profiles,
   private browsing and cleared storage could therefore create many
   installations operated by the same person. The database query correctly
   counted rows, but the presentation encouraged a person-count interpretation.
2. **Active mix counted installation rows, not people.** A row was active when
   its mutable `last_seen_at` fell inside the window. The result could not state
   how many humans were active.
3. **Roku versions were overwritten.** Roku used a channel client ID for the
   installation and wrote the latest application version onto the same row.
   “Roku: 2” therefore meant two installation IDs, not two versions, while the
   two known versions could not both be displayed.
4. **Page views were aggregated before evidence was retained.** The daily
   table stored counters by day/path/source/device. It had no event ID,
   installation or session, so retries and the exact contributors could not be
   reconstructed afterward.
5. **Legacy and current traffic shared a total.** Source and device dimensions
   were added later, leaving older traffic categorized as unknown while still
   participating in headline totals.
6. **Account links were summed across platforms.** A linked account could
   contribute once to more than one platform and inflate the headline “account
   links” number relative to distinct accounts.
7. **The employee client sent an unsupported source value.** `employee-app`
   was produced by the employee application but rejected by the endpoint’s
   prior validation enum, preventing a complete platform record.

## What can and cannot be concluded about the old figures

The old 15-installation total may describe 15 stored installation identifiers.
It cannot prove that 15 people or 15 physical devices used the service. The
legacy aggregate does not retain enough evidence to attribute each identifier
to a browser lifecycle, automation session, reinstall or person. It would be
misleading to “correct” the total to two merely because two people are known.

The migration therefore preserves the old rows, labels them `legacy`, removes
them from authoritative totals and starts a verified baseline. The operational
audit command can explain all v2 contributing records without revealing raw
identifiers:

```sh
pnpm analytics:audit
```

The command reports grouped installation/version/event evidence and verifies
that accepted production page-event count equals the v2 daily aggregate.

## Corrective architecture

- Unique event IDs make page and presence ingestion idempotent.
- Raw ledgers retain privacy-safe evidence without IP addresses, raw referrers
  or user-agent strings.
- Production, internal, preview and development contexts are separate.
- Verified and legacy data never share an authoritative aggregate row.
- Known accounts, anonymous installations, sessions, page views and application
  versions are separate Studio measures.
- Application history uses product, release channel, semantic version and build
  number. An upgrade adds history to an installation rather than adding an
  installation.
- Archive corrections create immutable revisions before the current snapshot
  changes.
- Administrator/editor exports pseudonymize identifiers.
- The Studio workbench uses fixed views and pagination with no page, table or
  nested scrollbars at supported desktop sizes.

## Acceptance control

Automated tests cover:

- two known accounts using separate web installations;
- one account using a Roku installation across two builds;
- the same Roku installation upgrading without becoming two installations;
- two physical Roku installations remaining distinct;
- duplicated event IDs;
- legacy and preview exclusions.

After deployment, the release must still complete the production evidence
reconciliation described in `ROLL_OUT.md`. Until that check passes, Studio
correctly retains a provisional quality badge when legacy evidence exists.
